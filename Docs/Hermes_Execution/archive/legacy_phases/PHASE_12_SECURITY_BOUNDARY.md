# Phase 12 Security Boundary — User Database Sandbox Runtime

## Boundary Summary

Phase 12 preserves SAFY's safer existing model. Sandbox adds an isolated runtime target, but it does not loosen SQL Guard, `/query/check`, `/query/execute`, driver policy, audit, or result persistence boundaries.

## `/query/check` No-Connection Rule

`/query/check` must not:

- open database connections
- execute SQL
- validate by touching a live DB/container
- refresh schema by querying the sandbox
- infer PASS from runtime availability

`/query/check` may use:

- request metadata
- target metadata
- sandbox state metadata
- schema cache generated by restore/load
- stored schema summaries
- SQL Guard analysis

If live schema access is needed, use `GET /sandboxes/{sandbox_id}/schema` against the existing cache or a separate explicitly controlled refresh operation, not `/query/check`.

## `/query/execute` Guard Requirements

`/query/execute` must require all existing controls:

- valid `check_id`
- matching `sql_hash`
- unexpired check state
- target binding
- matching `sandbox_id` when target is `sandbox`
- no consumed check
- SQL Guard approval
- read-only policy

Sandbox target binding must be part of the check state. A check for one sandbox cannot execute against another sandbox or against a real DB.

## Readonly Sandbox Runtime User

After restore/import/init:

- owner/admin user may be used only for internal restore/init/setup
- user/agent query execution must use a generated readonly sandbox user
- readonly user receives minimum required read privileges
- write privileges must not be granted to runtime query user
- runtime query code must not use owner/admin credentials

This is mandatory even though the sandbox is isolated, because agent-safe access still requires least privilege.

## Read-Only SQL Policy

Phase 12 blocks write and procedural execution. Allowed baseline is `SELECT`, `WITH ... SELECT`, and already-approved metadata reads. Blocked baseline includes `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `MERGE`, `CALL`, `EXEC`, `EXECUTE`, procedural blocks, multi-statement execution, and all DDL/DML/write operations.

## No Raw Secret Persistence

Do not persist:

- raw DSNs
- raw passwords
- owner/admin credentials
- generated runtime passwords in plain metadata
- private backup contents
- provider secrets

If secrets must exist for runtime operation, use existing secret handling or ephemeral process environment. Metadata may store references or redacted handles only.

## No Result Row Persistence

Do not persist result rows in:

- sandbox metadata
- schema cache
- audit logs
- query history
- planning or validation reports

API/UI may return rows temporarily in HTTP responses. Audit may store row count and error code only.

## Metadata-Only Audit

Allowed audit fields:

- timestamp
- action
- sandbox id or sandbox id hash
- project/workspace id
- DBMS type
- lifecycle/operation status
- `sql_hash`
- `check_id`
- row count
- error code

Forbidden audit fields:

- raw secrets
- raw DSNs
- raw passwords
- result rows
- full SQL result data
- full backup contents

Full SQL text should be avoided in sandbox audit unless an existing SAFY policy explicitly permits safe storage; `sql_hash` is the default.

## Backup Privacy

Supabase backup is private test data:

- not committed to the repository
- not copied into reports
- not persisted in sandbox metadata except redacted path/hash metadata when necessary
- env-gated for restore validation
- default validation may skip private restore as `SKIPPED_SUPABASE_BACKUP_RESTORE_NOT_REQUIRED`
- if gate enabled, missing backup is `BLOCKED_BACKUP_MISSING`
- if gate enabled, restore failure is `BLOCKED_BACKUP_RESTORE_FAILED`
- successful gated restore is `PASS_SUPABASE_BACKUP_RESTORE`

## Path Confinement for Mounted Backup

Restore/import must confine backup access:

- only allow explicit user-selected paths or configured import roots
- reject path traversal and unexpected symlinks where possible
- mount backup read-only into containers
- avoid broad host directory mounts
- never mount the repository root just to access a backup
- never copy private backup contents into tracked files

## Resource Limits

Sandbox runtime should define limits for:

- CPU
- memory
- disk/volume size where supported
- restore timeout
- query timeout
- maximum returned rows
- maximum concurrent sandbox operations
- log size and audit retention

Limit failures must fail closed and report metadata-only errors.

## Network Isolation Policy

Sandbox containers should run on isolated Docker networks by default:

- no unnecessary public port exposure
- only SAFY backend may connect to sandbox runtime where possible
- no outbound network from sandbox unless explicitly required for DBMS operation
- per-project/workspace separation prepared in network names and metadata

## Docker Availability Gate

If Docker gate is enabled, Docker availability must be checked before claiming runtime validation. If Docker is unavailable or not running, the status is:

```text
BLOCKED_DOCKER_ENGINE_NOT_RUNNING
```

If Docker gate is disabled, Docker-heavy tests may be skipped:

```text
SKIPPED_DOCKER_NOT_REQUIRED
```

Reports must not claim Docker runtime validation passed unless it actually ran.

## Fail-Closed Behavior

The system must fail closed when:

- sandbox state is missing or corrupt
- target binding does not match check state
- check is expired or consumed
- SQL hash mismatches
- SQL Guard rejects the query
- readonly runtime user cannot be created
- restore/import fails
- Docker gate is enabled and Docker is unavailable
- backup gate is enabled and backup is missing
- active sandbox policy would be violated without explicit user action

Conflict resolution rule: if any Phase 12 feature conflicts with established SAFY safety boundaries, preserve the safer model and document the limitation.
